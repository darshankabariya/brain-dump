      Part A · Architecture≈ 30 min

      Five worlds, one dependency direction

      The workspace has about 50 crates. They group into five "worlds", and dependencies only ever point downward: the chain depends on the machine, the machine on the twin types, the twin types on the math core.

      Two things stand out. synthesizer/src is only 65 files but carries the most change: the VM is where consensus rules, limits and block processing live, so every protocol upgrade touches it. And circuit/ is huge but quiet. It's mature, and it only changes when the language gains a new operation.

      A2World 1: the math core

      Open each card for what the crate owns, the types you'll meet, and what to be careful with.

      utilities/5.3k linesSerialization, bit manipulation, parallelism helpers and derive macros used by every other crate.
      Owns
      • ToBytes / FromBytes: the canonical little-endian binary encoding used for IDs, hashes and storage.
      • ToBits / FromBits; cfg_iter!-style macros that switch between rayon and sequential iteration.
      • utilities/derives: procedural macros.
      Touch with care. Byte encodings feed into transaction and block IDs, so a changed encoding is a consensus change. Recent work bounds every length-prefixed read (#3391, #3413 open) so malformed input can't force huge allocations.
      fields/5.5k linesPrime-field arithmetic: the numbers everything else is made of.
      Owns
      • Fp256, Fp384 and the extension towers Fp2, Fp6, Fp12 (needed for pairings).
      • Traits Field, PrimeField, FftField; Legendre symbols; square roots.
      Open work

      Faster inversion (#3112). A self-contained, benchmarkable problem.

      curves/9.3k linesBLS12-377 (the pairing curve for proofs) and Edwards-BLS12 (the curve for addresses, signatures and encryption).
      Owns
      • Short Weierstrass and twisted Edwards templates; affine and projective points; pairing.
      • Point (de)serialization, including compressed forms with sign flags.
      Recent hardening. Rejecting non-canonical encodings: the Edwards x = 0 sign flag (#3425), the infinity encoding (#3397), and the Weierstrass y = 0 sign flag (#3422, open). Two encodings of the same point would mean two different IDs for the same object.
      algorithms/21.1k linesThe proof system and its heavy machinery: Varuna, polynomial commitments, FFT, MSM, R1CS, the SRS, Poseidon.
      Map
      • snark/varuna/: varuna.rs (prove, verify, batch), ahp/ (the algebraic protocol: indexer, prover rounds, verifier), data_structures/ (keys, proofs), mode.rs (hiding / non-hiding).
      • polycommit/: kzg10 and sonic_pc.
      • fft/: evaluation domains, dense and sparse polynomials. msm/: multi-scalar multiplication, the dominant proving cost.
      • r1cs/: constraint systems. srs/: the universal SRS. crypto_hash/: the Poseidon sponge (Fiat–Shamir) and SHA-256.
      • algorithms/cuda: GPU kernels behind the cuda feature.
      Recent

      CPU proving algorithm speed-ups (#3399), Varuna test vectors (#3437), and a Poseidon compression simplification (#3351, open). Open issues: faster common-instance verification (#2952); unbounded batch_sizes when deserializing a proof (#3160, a bug).

      Touch with care. Soundness lives here. Any change to transcript order, challenge derivation or serialization changes which proofs verify.

      console/network87 commits in 6 moThe most-edited file set outside the synthesizer, because every consensus upgrade adds a version and activation heights here.

      consensus_heights.rs defines ConsensusVersion V1–V21 and the height at which each activates on mainnet, testnet and canary. Network constants such as program size limits, transaction size limits, maximum mappings and array sizes are often arrays indexed by version. Issue #3378 proposes making that pattern uniform.

      Known issue. #3411: a global OnceLock caches consensus heights per process, so the first network queried wins. A draft fix is in #3414. Worth reading as an example of the subtle bugs this layer can have.
      circuit/environment23 commits in 6 moThe engine that records constraints while circuit types run.

      A thread-local R1CS builder. Every circuit operation calls into it to allocate variables and enforce a·b = c. Tests use assert_scope!(num_constants, num_public, num_private, num_constraints) to pin the exact cost of each gadget. A regression in those numbers changes deployment costs, and it can change verifying keys.

      It also enforces synthesis limits (constraints and variables) during CheckDeployment. Robustness work continues in #3344 (open) and #3374 (draft).

      Part B · Cross-cutting systems≈ 20 min

      The rules that span every crate

      Most bugs and most review comments come from these six systems, not from any single crate.

      B1Consensus versioning

      Every behaviour change ships behind a ConsensusVersion that activates at a height, testnet first and mainnet later. The pattern appears in four forms:

      • Branching on version: if consensus_version >= ConsensusVersion::V20 { … } inside verification and finalize.
      • Versioned functions: deployment_cost_v1 … _v4 in process/src/cost.rs.
      • Versioned constants: limits stored per version in console/network.
      • Versioned encodings: record version 0/1, DynamicRecord v2, Varuna versions.

      Tests follow the same structure. synthesizer/src/vm/tests/test_vN checks behaviour before and after each activation height, and a placeholder version is added before a feature lands (#3353).

      Rule of thumb

      If your change can make any historical block validate differently, it needs a version gate. If you're unsure, say so in the PR description.

      B2Serialization: three encodings, all consensus-relevant

      EncodingFilesUsed for
      Bytesbytes.rs (ToBytes/FromBytes)Network messages, storage, and the input to ID hashes
      Stringparse.rs, string.rs (FromStr/Display)Program text, literals, aleo1… addresses, CLI and REST
      Serde / JSONserialize.rsREST API and SDK interchange

      Most types have all three. Invariants: round-trips are exact (prop-tests feature, #3405); decoding is canonical (one valid encoding per value); decoding is bounded (no attacker-controlled allocation sizes); decoding never panics (#3352, #3116). Recent work (#3398, zero-copy deserialize) shows performance matters here too, because nodes decode many blocks and transactions.

      B3Concurrency and state

      • Process: stacks behind an RwLock; ProcessExclusiveGuard ensures only one writer at a time (deadlock fix #3275).
      • VM: operations that must not interleave (adding a block, speculating) go through one sequential_ops thread. Its occupancy is a latency bottleneck being worked on (#3441).
      • Store: atomic_speculate and atomic_finalize apply finalize in an atomic batch that is rolled back on failure. Speculative reads versus locks: #3438; potential deadlock: #3193.
      • Caches: partially_verified_transactions (an LRU keyed with the consensus version since #3299); memoized type checks.
      • Tooling: the locktick feature instruments locks to find contention.

      Reading the signal

      D2A 90-day plan

      Weeks 1–2 · OrientRead Inside snarkVM and this atlas. Build the workspace, run one synthesizer expectation test and one ledger test. Trace VM::execute end to end.
      Weeks 3–4 · First PRPick a small bug (#3116, #3160, #3048). Comment first, write a failing test, then fix it. Follow AGENTS.md exactly.
      Month 2 · Own a sliceChoose theme 1 or 2. Land two or three PRs in one area so reviewers start associating you with it: a fuzzing harness, or a benchmark plus optimization.
      Month 3 · LeadWrite an issue or proposal in that area with data (fuzz findings, profiles). Offer to take on an open proposal such as #3426 or #3230.
      How to write PRs reviewers like
      • One concern per PR, with tests. Say explicitly whether it affects consensus and why or why not.
      • Target staging. Run clippy with -D warnings and the pinned nightly fmt.
      • For performance work, include benchmark numbers and proof that outputs are unchanged. For hardening, include the malformed input as a regression test.
      • Don't add new files, crates, dependencies or traits without asking first. The team's rules require approval.
