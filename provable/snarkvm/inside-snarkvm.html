    Inside snarkVMHow Aleo turns programs into proofs, how validators check them, and how the pieces of the codebase fit together.

    This guide is for someone opening the snarkVM repository for the first time. It starts with the maths you need, then describes Aleo as a working system, then walks through the crates and the execution pipeline, and ends with what happens in real transactions and a reading plan for the code.

    The userruns the program on their own device and produces a zero-knowledge proof.
    The validatorchecks the proof and runs only the small public part of the program.
    snarkVMdoes both halves, and it also defines what counts as a valid transaction, block and ledger state.

      Part I · Prerequisites≈ 25 min

      The maths you need, and only that

      You don't need to be a cryptographer to read snarkVM. You do need a working picture of six ideas, because the code uses them everywhere. Each chapter below ends with where that idea lives in the repository.

      01Finite fields: the native number type

      A finite field is arithmetic modulo a prime p. You can add, subtract, multiply, and divide by anything except zero, and the result always wraps back into the range 0…p-1. With p = 7: 5 + 4 = 2, 3 × 5 = 1, so 3 and 5 are each other's inverse.

      In snarkVM the prime is about 253 bits long: it's the scalar field of the BLS12-377 curve. A value of that type is called a Field, and it's the machine word of the whole system. Proofs are statements about equations over this field, so anything a circuit touches has to be expressed as field elements at some point.

      The practical consequence: field operations are cheap in a circuit, and "normal" integer operations are expensive. A u64 addition must also prove there was no overflow, which means breaking the number into 64 bits and constraining each bit to be 0 or 1. Adding two field values is essentially free by comparison. This is why Aleo programs expose field as a first-class type, and why constraint counts matter so much in reviews.

      In the code
      • fields/: the field traits and concrete prime fields (Fp256, Fp384).
      • console/types/field and circuit/types/field: the Aleo Field type, in its native and in-circuit forms.
      • console/types/integers and circuit/types/integers: the u8…u128 and i8…i128 types, built out of bits.
      Why is u64 addition more expensive than field addition inside a proof?

      A field addition wraps modulo p, which is exactly what the proof system does anyway. A u64 addition has to behave like a 64-bit integer, so the circuit must decompose values into bits, constrain each bit to be boolean, and check for overflow. That is dozens of constraints instead of about zero.

      02Elliptic curves, keys, and the "curve inside a curve"

      An elliptic curve group is a set of points with an addition rule. Given a fixed generator point G and a secret number s, computing s·G (adding G to itself s times, done quickly) is easy. Going backwards from s·G to s is the discrete logarithm problem, which classical computers can't solve for large groups. That asymmetry gives you key pairs: s is private, s·G is public.

      snarkVM uses two curves, and seeing why is one of the first "aha" moments in the codebase:

      CurveRoleWhy this one
      BLS12-377The SNARK's curve. Proofs, verifying keys and polynomial commitments live here.It's pairing-friendly: it supports a bilinear map that the proof system needs for KZG commitments.
      Edwards-BLS12
      (a twisted Edwards curve)      		Everything a program touches: the group type, addresses, signatures, record encryption.Its coordinates are elements of BLS12-377's scalar field, the same field circuits work in. So adding points inside a circuit is native arithmetic and relatively cheap.

      This pattern is called an embedded curve. If addresses used BLS12-377 directly, every signature check inside a proof would mean emulating a foreign field, which would be enormously expensive.

      In the code
      • curves/: both curves, their parameters and pairing code.
      • console/types/group and scalar: points on Edwards-BLS12, and the scalars that multiply them.
      • console/network/src/mainnet_v0.rs: the PairingCurve and the twisted Edwards coefficients A and D.
      Keep in mind

      Both curves depend on discrete logarithms being hard. Shor's algorithm on a large quantum computer would break that. It's the root of the post-quantum discussion: addresses, record encryption and Varuna proofs all rely on these curves.

      03Hashes, commitments and Merkle trees

      Hash functions map any input to a fixed-size fingerprint. snarkVM carries several, because their cost inside a circuit varies enormously:

      • Poseidon (psd2, psd4, psd8) is designed for field arithmetic and needs only a few hundred constraints. It's used for most internal hashing: tags, IDs, key derivation.
      • BHP (Bowe–Hopwood–Pedersen, in 256/512/768/1024-bit variants) and Pedersen are hashes built from curve points. They're used for commitments and Merkle trees.
      • Keccak / SHA-3 / SHA-256 are bit-oriented and expensive in circuits. They exist so Aleo programs can interoperate with Ethereum and Bitcoin data.

      A commitment Commit(m, r) is a sealed envelope. It hides m (thanks to the random r), and it binds you: you can't later open it to a different m. Every record on Aleo is represented on-chain by a commitment, so the chain can refer to a record without revealing it.

      A Merkle tree hashes many leaves pairwise up to a single root. To prove a leaf is in the tree you reveal only the sibling hashes on its path, called a Merkle path. Aleo keeps a global tree over all blocks, transactions, transitions and record commitments. Its root is the global state root. When you spend a record, the proof shows inside the circuit that the record's commitment has a valid Merkle path to a recent state root, without revealing which leaf it is.

      In the code
      • console/algorithms and circuit/algorithms: BHP, Pedersen, Poseidon, Keccak, SHA-3 and ECDSA, in both worlds.
      • console/collections: Merkle trees.
      • console/program/src/state_path: the StatePath that proves a record commitment is in the global tree.

      04Arithmetic circuits and R1CS

      A zero-knowledge proof proves a statement of a very specific form: "I know values that satisfy this system of equations." The equations are the circuit. snarkVM uses R1CS (Rank-1 Constraint System), where every equation looks like

      (linear combination A) × (linear combination B) = (linear combination C)

      A classic toy example: prove you know x such that x³ + x + 5 = 35, without revealing x = 3. You flatten the formula into multiplication steps:

      // one multiplication per constraint
v1 = x  · x         // constraint 1
v2 = v1 · x         // constraint 2
(v2 + x + 5) · 1 = 35   // constraint 3 (additions are free)

// witness (secret assignment):  x = 3, v1 = 9, v2 = 27
// public input:                 35

      The full set of values (x, v1, v2) is the witness or assignment. Some variables are public, and the verifier sees them. Others are private, and only the prover knows them. snarkVM models this with three modes: Mode::Constant (fixed in the circuit itself), Mode::Public and Mode::Private.

      Circuits have a fixed shape, and that has three consequences for Aleo programs:

      • No unbounded loops. Every loop must be unrolled to a known number of iterations at compile time.
      • Both branches of an if are computed. The result is chosen with a ternary. There's no "skipping" work in a circuit.
      • Cost is measured in constraints and variables, not time. Deployment cost is derived from how big the function's circuit is.
      In the code
      • algorithms/src/r1cs: the constraint-system representation.
      • circuit/environment: the Environment that records constraints as circuit types run, plus Mode, Inject (bring a value into the circuit) and Eject (read it back out).
      If a function has if cond { a() } else { b() }, what does the circuit contain?

      Constraints for both a() and b(), plus a selection constraint that picks the output based on cond. The proof cost is the sum of both branches.

      05zkSNARKs, and the one snarkVM uses: Varuna

      A zkSNARK (zero-knowledge Succinct Non-interactive ARgument of Knowledge) is a system with three steps:

      Setupcircuit → proving key + verifying key
      →
      Proveproving key + public inputs + secret witness → proof π
      →
      Verifyverifying key + public inputs + π → accept / reject

      It guarantees four properties. Completeness: honest proofs verify. Soundness: false statements can't be proven, except with negligible probability. Zero-knowledge: the proof reveals nothing about the witness beyond the truth of the statement. Succinctness: proofs are small and quick to check, however big the computation was.

      How Varuna works, at intuition level

      snarkVM's proof system is Varuna, a descendant of Marlin. Its pipeline:

      1. The R1CS is encoded as polynomials. "The constraints are satisfied" becomes "certain polynomial identities hold."
      2. The prover commits to those polynomials using KZG polynomial commitments on BLS12-377. A KZG commitment is a single curve point that pins down a whole polynomial.
      3. The verifier, made non-interactive using hashes (Fiat–Shamir), picks random points. The prover opens the commitments there, and pairings check that the openings are consistent. A polynomial identity that holds at a random point almost certainly holds everywhere.

      Two properties of Varuna shape the rest of Aleo:

      • Universal setup. A single universal SRS (structured reference string, a long list of curve points from a one-time ceremony) serves every circuit. Deploying a new program doesn't need a new trusted setup. snarkVM just "indexes" the circuit against the universal SRS to derive that function's proving and verifying keys.
      • Batching. One Varuna proof can cover many different circuits and many instances of each. That's why an Aleo execution with several nested function calls carries one proof, not one per call.
      In the code
      • algorithms/src/snark/varuna: the prover and verifier (ahp/ holds the algebraic core).
      • algorithms/src/polycommit: kzg10 and sonic_pc (the KZG-based commitment scheme Varuna uses).
      • algorithms/src/fft and msm: the heavy number-crunching (polynomial FFTs, multi-scalar multiplication). algorithms/cuda holds GPU acceleration.
      • synthesizer/snark: thin wrappers ProvingKey, VerifyingKey, Proof and Certificate used by the rest of the VM.
      • parameters/: the universal SRS powers, pre-computed keys for credits.aleo, and genesis blocks.

      06Two state models, and three Rust type parameters

      Blockchains track state in one of two ways. The account model (Ethereum) keeps a global table of balances and storage that transactions mutate. The UTXO model (Bitcoin, Zcash) keeps a set of unspent "notes". A transaction consumes some and creates new ones. Aleo uses both:

      • Records are UTXO-style, encrypted, and owned by one address. This is where privacy lives.
      • Mappings are account-style public key→value tables per program. This is where shared state lives.

      Finally, three generic type parameters appear on almost every snarkVM type. Once you recognise them, the signatures stop looking scary:

      ParameterMeaningTypical concrete type
      N: NetworkWhich chain: its constants, hash functions, curve and consensus heights.MainnetV0, TestnetV0, CanaryV0
      A: circuit::Aleo<Network = N>The circuit environment that records constraints for network N.AleoV0, AleoTestnetV0, AleoCanaryV0
      C: ConsensusStorage<N>The storage backend for the ledger.In-memory, or RocksDB (the rocks feature)

      So Process::execute::<A, R>(authorization, rng) reads as "execute on this network, recording constraints in circuit environment A, using randomness R."

      08Accounts: one seed, four keys, four powers

      An Aleo account derives a chain of keys from one random seed. Each key along the chain can do less than the one before it, which is what makes delegated proving and read-only access possible.

      Two practical consequences:

      • You can hand your view key to an auditor, accountant or regulator. They can read your history but can't move funds. This is the "selective disclosure" feature that institutional users care about.
      • Proving is expensive, so a phone can sign an authorization with the private key and let a proving service build the proof. The service learns the inputs but can't change them or spend anything else.

      There's also a graph key (console/account/src/graph_key), derived from the view key. It produces sk_tag, which is used to compute record tags (chapter 10).

      Note that the Aleo address is a curve point. That matters for the quantum discussion: unlike Ethereum, which publishes a hash of the public key, every Aleo address exposes its public point from day one.

      09Programs: functions, finalize, records, mappings

      A deployed program is a text file of Aleo instructions. Here is a small token program with a private transfer and a public transfer:

      program token.aleo;

// Private state: an encrypted UTXO owned by an address.
record token:
    owner  as address.private;
    amount as u64.private;

// Public state: an on-chain key→value table.
mapping account:
    key   as address.public;
    value as u64.public;

// Runs on the USER's machine and is proven. Validators see nothing private.
function transfer_private:
    input r0 as token.record;
    input r1 as address.private;
    input r2 as u64.private;
    sub r0.amount r2 into r3;                 // underflow fails the proof
    cast r1 r2 into r4 as token.record;       // new record for the recipient
    cast r0.owner r3 into r5 as token.record; // change back to the sender
    output r4 as token.record;
    output r5 as token.record;

// Proven part: produces a Future that carries public arguments.
function transfer_public:
    input r0 as address.public;
    input r1 as u64.public;
    async transfer_public self.caller r0 r1 into r2;
    output r2 as token.aleo/transfer_public.future;

// Runs on EVERY VALIDATOR, not proven. Reads and writes mappings.
finalize transfer_public:
    input r0 as address.public;
    input r1 as address.public;
    input r2 as u64.public;
    get.or_use account[r0] 0u64 into r3;
    sub r3 r2 into r4;
    set r4 into account[r0];
    get.or_use account[r1] 0u64 into r5;
    add r5 r2 into r6;
    set r6 into account[r1];
      ElementWhere it runsProven?Touches
      functionUser's deviceYes, alwaysInputs, records, calls to other functions
      closureInside a function's circuitYes, as part of its callerOnly its inputs
      finalize (via async / Future)Every validator, in block orderNo, it's re-executedMappings, block height, randomness
      constructorValidators, at deploy or upgradeNoMappings. Decides whether an upgrade is allowed.
      record, struct, mappingType declarations: private data, composite data, public storage.

      Why the split between function and finalize? A proof is made before the transaction is ordered in a block. It can't know the current value of a public balance, because another transaction might change it first. So anything that reads or writes shared state is moved into finalize and runs after ordering. It's the same reason Ethereum re-executes everything, applied only to the part that needs it.

      The program language has grown through consensus upgrades. Program upgrades with an edition number and a constructor arrived in V9. ECDSA verification arrived in V11. snark.verify, dynamic dispatch and much larger size limits arrived in V14–V16. More mappings per program arrive in V21.

      In the code
      • synthesizer/program/src: Program, plus function/, closure/, finalize/, constructor/, mapping/ and import/.
      • synthesizer/program/src/logic/instruction: every opcode (add, hash.bhp256, cast, call, async…).
      • synthesizer/program/src/logic/command: finalize-only commands (get, get.or_use, set, contains, remove, rand.chacha, branch, position, await).
      • synthesizer/program/src/resources: credits.aleo, the built-in token and staking program.

      10Records: the private coin, from birth to spend

      A record is defined in console/program/src/data/record/mod.rs:

      pub struct Record<N, Private> {
    owner:   Owner<N, Private>,                        // the address that can spend it
    data:    IndexMap<Identifier<N>, Entry<N, Private>>, // e.g. amount
    nonce:   Group<N>,                                 // nonce = G · randomizer
    version: U8<N>,                                    // commitment scheme version
}

      The type parameter Private is either Plaintext or Ciphertext, so the same struct describes the decrypted and encrypted forms. The life of a record has three stages:

      Encryption: how only the owner can read it

      From record/encrypt.rs: the creator picks a random randomizer and publishes nonce = G·randomizer. They compute the record view key (owner_address · randomizer).x and encrypt the fields with it. The owner can recompute the same key as (view_key · nonce).x, because view_key · G · randomizer = randomizer · address. This is a Diffie–Hellman exchange on Edwards-BLS12. Wallets try this against every new record on chain. If decryption yields their own address as owner, the record is theirs.

      Spending: serial numbers make spends unlinkable

      From record/serial_number.rs and record/tag.rs:

      H             = HashToGroup(commitment)
gamma         = sk_sig · H
serial_number = Commit_bhp512(commitment, Hash(gamma))
tag           = Hash_psd2(sk_tag, commitment)

      The serial number is deterministic, so spending the same record twice produces the same serial number, and validators reject duplicates. That's double-spend protection. But it's computed from a secret key, so nobody else can connect a serial number to the commitment it came from. The chain learns "some record was spent", never "record #4711 was spent". The spending proof also contains a Merkle path showing the commitment is in the global state tree. That path is checked inside the circuit, against the global_state_root named in the execution.

      What stops Alice from spending the same record in two different blocks?

      Both spends would publish the same serial number, because it's deterministic from the commitment and her sk_sig. The validator checks serial numbers for uniqueness within the transaction, within the block and against the whole ledger, and rejects the second spend.

      11Transactions and transitions

      One function call produces one transition. A user's action, which may call several functions through nested calls, produces an execution: a set of transitions with one batched proof. Add a fee and you have a transaction.

      There are exactly three transaction variants:

      pub enum Transaction<N> {
    Deploy(TransactionID, DeploymentID, ProgramOwner, Box<Deployment>, Fee),
    Execute(TransactionID, ExecutionID, Box<Execution>, Option<Fee>),
    Fee(TransactionID, Fee),   // what remains of a rejected transaction
}

      Notice what a transition reveals: the program ID and function name are plaintext. An observer can see "someone called token.aleo/transfer_private" but not who, to whom or how much. The tpk (transition public key) and tcm (transition commitment) tie the encrypted inputs and outputs to a per-transition secret, the transition view key (tvk). The scm commits to the signer.

      Accepted, rejected, aborted

      Being included in a block doesn't guarantee the transaction succeeded. When the block is built, each transaction becomes a ConfirmedTransaction:

      • AcceptedDeploy / AcceptedExecute: the proof was valid and finalize succeeded. State changes apply.
      • RejectedDeploy / RejectedExecute: the proof was valid, but finalize failed (for example an underflow on a public balance). The original is replaced by a Transaction::Fee, so the fee is still charged, and the rejected part is kept for the record.
      • Aborted: couldn't even be processed, for example a double spend or a missing fee. Only its ID is listed, in aborted_transaction_ids.

      12Blocks, consensus, and the coinbase puzzle

      From ledger/block/src/lib.rs:

      pub struct Block<N> {
    block_hash, previous_hash,
    header:                   Header,        // Merkle roots + metadata
    authority:                Authority,     // Beacon(signature) | Quorum(subdag)
    ratifications:            Ratifications, // Genesis | BlockReward | PuzzleReward
    solutions:                Solutions,     // coinbase-puzzle solutions from provers
    aborted_solution_ids,
    transactions:             Transactions,  // ConfirmedTransaction list
    aborted_transaction_ids,
}

      The header commits to everything with Merkle roots: previous_state_root, transactions_root, finalize_root (the result of all the mapping updates), ratifications_root, solutions_root and subdag_root. Its metadata holds the network ID, round, height, cumulative weight, puzzle targets and timestamp. Because finalize_root is in the header, two validators that computed different mapping state for the same block produce different block hashes. Any disagreement is caught immediately.

      Consensus: AleoBFT

      Consensus runs in snarkOS, but its data structures live in snarkVM (ledger/narwhal/*, ledger/committee). The design is Narwhal + Bullshark:

      1. Validators in the committee (Committee: members with stake, an open flag and a commission) each propose a batch of transmissions (transactions and puzzle solutions) every round.
      2. Other validators sign it. Once enough stake has signed, it becomes a batch certificate. Certificates reference ones from the previous round, which forms a DAG.
      3. A leader certificate is committed Bullshark-style. Everything it references and hasn't been committed yet forms a subdag.
      4. snarkVM turns the subdag into a block. The block's authority is Quorum(subdag), and the genesis block uses Beacon(signature).

      The committee changes with staking activity through credits.aleo bonding and unbonding, which is applied with a lookback: a committee takes effect a fixed number of rounds after it's formed.

      The coinbase puzzle

      Separately from validators, provers compete to find puzzle solutions that meet a difficulty target tied to the current epoch (ledger/puzzle). Solutions go into blocks, and provers are paid through the PuzzleReward ratification, while validators receive BlockReward. The idea is to reward hardware that is good at the same kind of work as ZK proving. The puzzle doesn't secure ordering; AleoBFT does that.

      13The crate map

      14The Network trait and consensus versions

      Everything chain-specific sits behind trait Network in console/network: the curve types, generators, domain separators, hash functions (N::hash_psd2, N::commit_bhp512…), size limits, fee constants and the Varuna prover and verifier instances. Three networks implement it: MainnetV0, TestnetV0 and CanaryV0.

      The most important file for anyone who changes behaviour is console/network/src/consensus_heights.rs. It lists the ConsensusVersions and the block height at which each one activates on each network:

      VersionWhat it changed (abridged from the source comments)
      V1–V3Genesis; block reward and execution cost algorithms; validator count and finalize RNG seed.
      V4Varuna version update.

      Why this file matters

      Every node must compute identical results for identical inputs, or the network forks. So any change that alters behaviour must be gated: if consensus_version >= V22 { new rule } else { old rule }. Old blocks must still validate with the old rules forever. That's why AGENTS.md says all changes must be backwards compatible, and why you'll see _v1…_v4 variants of functions such as deployment_cost.

      15The central idea: console and circuit twins

      Almost every type and algorithm in snarkVM is written twice, with the same structure and the same API:

      During a real execution, snarkVM runs both. The console version produces the actual outputs quickly and gives clear errors. The circuit version builds the R1CS and its witness, which Varuna then proves. At the end the circuit's outputs are ejected and must equal the console outputs.

      If the two versions ever differ, you get one of two failures:

      • Circuit stricter than console: valid transactions can't be proven, and users get stuck.
      • Circuit looser than console: a proof could be made for something the console would reject. That's a soundness bug, the most serious kind in a ZK system.

      That's why the review checklist in AGENTS.md says "circuit constraints match console logic exactly", and why tests compare outputs and constraint counts across the two.

      16synthesizer/program: programs as data

      This crate turns program text into typed Rust structures, and back. Program::from_str parses (parse.rs); bytes.rs and serialize.rs give the binary and JSON forms stored on chain. A Program holds its ID, imports, structs, records, mappings, closures, functions, an optional constructor, and views (read-only finalize-style helpers).

      Instructions live in logic/instruction. Each opcode has two implementations: evaluate (console) and execute (circuit), following the twin pattern again. Finalize-only commands live in logic/command, and logic/finalize_operation defines the effects finalize can have on storage:

      pub enum FinalizeOperation<N> {
    InitializeMapping(mapping_id),
    InsertKeyValue(mapping_id, key_id, value_id),
    UpdateKeyValue(mapping_id, key_id, value_id),
    RemoveKeyValue(mapping_id, key_id),
    ReplaceMapping(mapping_id),
    RemoveMapping(mapping_id),
}

      These operations are recorded per confirmed transaction and hashed into the block's finalize_root.

      17Process, Stack and CallStack

      Three types in synthesizer/process do the real work.

      Process is the registry of all deployed programs. It holds the universal SRS and a map from ProgramID to Stack, with credits.aleo loaded at start-up.

      Stack is one per program. It holds the program plus everything derived from it: register types for every function, closure, finalize and view; proving and verifying keys per function; the program address, checksum and per-component checksums; the edition and owner. It also keeps a weak reference back to all stacks, so a call to another program can be resolved.

      CallStack is the mode a function runs in. The same execute_function code path serves very different purposes depending on this enum:

      ModeUsed forProduces
      AuthorizeBuilding the signed requests for a call treeAuthorization
      AuthorizeMocked, AuthorizeRequestsAuthorization variants for simulations and multi-request call treesAuthorization
      SynthesizeGenerating keys when a program is deployedProving and verifying keys
      CheckDeploymentValidators re-synthesizing a deployment, with constraint and variable limitsAssignments, which are checked against certificates
      EvaluateRunning natively with no circuitOutputs only
      ExecuteReal execution with proof generationTransitions + assignments in a Trace
      PackageRunLocal runs by developer toolingAssignments

      Registers (stack/registers) are the working memory: r0, r1… Each holds a console value and, in circuit modes, the matching circuit value. register_types and finalize_types are computed once when the program is added, so type errors are caught at deployment, not at runtime.

      18The execution pipeline, step by step

      This is the path a wallet follows to create an execute transaction. Top-level entry: VM::execute in synthesizer/src/vm/execute.rs.

      Step 1: Authorize (sign what you intend to do)

      VM::authorize → Process::authorize → Stack::authorize. For the root call and every nested call, the wallet builds a Request (console/program/src/request):

      Request { signer, network_id, program_id, function_name,
          input_ids, inputs, signature,
          sk_tag, tvk, tcm, scm, is_dynamic }

      The signature covers the function and the input IDs (hashes or commitments of the inputs). The tvk (transition view key) is a fresh per-transition secret used to encrypt private inputs and outputs. All the requests together form an Authorization. This is the object you can hand to a delegated prover.

      Step 2: Execute (run twice, build the circuit)

      Process::execute → Stack::execute_function in stack/execute.rs, in CallStack::Execute mode. Reading the source comments in order, for each request:

      1. Check the network ID and that input types match the function signature.
      2. Inject the transition public key tpk as Public and the whole request as Private. Inject is_root and the parent as Public.
      3. Verify the request inside the circuit: signature, input IDs and tvk. This is what ties the proof to the signer's key.
      4. Store the inputs into registers, as console values and as circuit values.
      5. Run each instruction. evaluate runs on console values and execute adds constraints. A call recurses into the callee's stack, which produces its own transition.
      6. Load the outputs, build the Response (encrypting private outputs, committing to records), and check the circuit is satisfied.
      7. Insert the transition and its assignment into the Trace.

      Step 3: Prepare inclusion (prove your input records exist)

      Trace::prepare(query) (process/src/trace). For every record input, fetch a StatePath from a node (through the Query trait in ledger/query) that proves the record's commitment is under a recent global_state_root. These become extra inclusion circuits.

      Step 4: Prove

      Trace::prove_execution runs Varuna once over all transitions' assignments plus the inclusion assignments, and produces one batched proof. The result is Execution { transitions, global_state_root, proof }.

      Step 5: Fee

      The same pipeline runs for credits.aleo/fee_private or fee_public (authorize_fee_*, execute_fee_authorization, Trace::prove_fee). The fee is bound to the execution ID. Transaction::from_execution combines the two, and the wallet broadcasts it to a snarkOS node.

      What's the difference between Process::evaluate and Process::execute?

      evaluate runs only the console side: fast, no constraints, no proof. It's useful for simulations and for computing outputs. execute also synthesizes the circuit and records the assignment into a Trace, so a proof can be made. Only an executed transition is valid on chain.

      19The validator side: verify, speculate, finalize

      On the other side of the network, snarkOS hands the transaction to snarkVM.

      Step 1: VM::check_transaction (synthesizer/src/vm/verify.rs)

      • Is it well-formed, and under the size limit for the current height?
      • Is the transaction ID correct and unique? Are the transition IDs, input IDs, serial numbers, tags, output IDs, commitments, nonces, tpks and tcms all unique, within the transaction and against the ledger?
      • Is the fee sufficient, and bound to this transaction?
      • Verify the Varuna proof against each function's stored verifying key and the declared global_state_root. The root must be one the ledger actually had.
      • For deployments: the program size and ownership checks, and the upgrade rules (edition, checksum, at least one key changed, constructor required after V9).

      Verification is the expensive part, so results are cached in partially_verified_transactions on the VM, and transactions are verified in parallel batches.

      Step 2: VM::speculate (vm/finalize.rs)

      When a validator builds a block from a committed subdag, speculate runs every transaction's finalize logic in order against a speculative copy of state (atomic_speculate). Each transaction comes out as accepted, rejected or aborted, with its list of FinalizeOperations, and the ratifications (rewards) are computed too. The results give the block's finalize_root.

      Step 3: VM::check_speculate

      When a node receives a block rather than building it, it re-runs the same speculation and checks that it gets identical ratifications, confirmed transactions and finalize root. This is the re-execution half of Aleo: public logic is recomputed by everyone, private logic is checked only through the proof.

      Step 4: Ledger::check_next_block → Ledger::advance_to_next_block → VM::add_next_block

      The ledger validates the block itself: hashes, header roots, authority (subdag certificates signed by enough stake), puzzle solutions, height, round and timestamp. It then calls VM::add_next_block, which commits everything through atomic_finalize: the block, transactions, transitions, new records, spent serial numbers and mapping updates, all in one atomic batch. Some VM operations must not interleave, so they're routed through a single sequential_ops thread.

      20The deployment pipeline

      A deployment publishes a program, and with it a verifying key for every function:

      pub struct Deployment<N> {
    edition:          u16,          // 0 at first deploy, bumped on upgrade
    program:          Program,
    verifying_keys:   Vec<(Identifier, (VerifyingKey, Certificate))>,
    program_checksum: Option<[U8; 32]>,  // required after its migration height
    program_owner:    Option<Address>,
}
      1. Developer side (VM::deploy → Stack::deploy): each function is synthesized in CallStack::Synthesize mode with dummy inputs to get its circuit. Varuna indexes it against the universal SRS to get the proving and verifying keys. A Certificate is produced for each verifying key, proving the key was derived honestly from the circuit.
      2. Validator side (verify_deployment.rs): the validator re-synthesizes each function in CheckDeployment mode, under constraint and variable limits, and checks the certificates. Without this, someone could deploy a program with a fake verifying key that accepts anything.
      3. Cost (process/src/cost.rs): storage cost for the bytes, plus synthesis cost based on the number of constraints and variables, plus a namespace cost for short names. Several versions exist, gated by consensus version.
      4. Finalize (Process::finalize_deployment): add the new Stack, initialize its mappings and run the constructor if there is one.

      Upgrades (since V9): a later deployment with a higher edition, checked by the program's own constructor logic. The constructor could require the owner's approval, forbid upgrades completely, or run a governance check. Process keeps old_stacks so it can roll back if a block fails.

      21Ledger, storage and queries

      The Ledger (ledger/src/lib.rs) is what snarkOS holds. It wraps the VM and adds the genesis block, the current epoch hash, the current committee and caches. Its files are named for what they do: check_next_block.rs, advance.rs, check_transaction_basic.rs, find.rs, get.rs, contains.rs, iterators.rs.

      Storage (ledger/store) is split into typed stores behind traits, all grouped under a ConsensusStore:

      StoreHolds
      BlockStoreBlocks, headers, the state-root tree, the height index
      TransactionStoreDeployments, executions, fees
      TransitionStoreTransitions, with inputs (serial numbers, tags) and outputs (commitments, records)
      FinalizeStoreMappings: the public state

      Each store has two backends in store/src/helpers: memory for tests and rocksdb for real nodes. Query (ledger/query) is how a prover gets state it doesn't have locally: state paths and the latest state root. It can be answered from a local ledger or from a node's REST API, which is what the SDK uses.

      22The cryptographic core, briefly

      You can treat algorithms/ as a black box for a long time. When you do open it:

      • snark/varuna/varuna.rs: the prover and verifier entry points. ahp/ holds the algebraic holographic proof (the interactive protocol before it's compiled with commitments). mode.rs defines a hiding (zero-knowledge) mode and a non-hiding mode. snarkVM instantiates Varuna in the hiding mode (synthesizer/snark/src/lib.rs).
      • polycommit/sonic_pc on kzg10: commit to polynomials, open them at points, and batch many openings.
      • fft/: evaluation domains and polynomial arithmetic. msm/: multi-scalar multiplication, the dominant proving cost.
      • srs/: the universal SRS. The real powers are loaded or downloaded by parameters/ on demand, with bounded downloads so a stalled mirror can't hang a node.
      • crypto_hash/: Poseidon sponge and SHA-256, used by Fiat–Shamir and elsewhere.

      Part IV · The real world≈ 10 min

      How it plays out in practice

      With the components in place, here is one real transaction end to end, and how the different pieces of software use snarkVM.

      23A private payment, end to end

      Alice pays Bob 100 units of a private token, for example a private stablecoin program. Alice uses a browser wallet, and Bob uses a mobile wallet.

      1. Alice's wallet scans the chain with her view key and finds a record with 250 units.
      2. It calls authorize for transfer_private(record, bob_address, 100). Her private key signs the request, and a fresh tvk is generated.
      3. It asks a node for the Merkle path of her record's commitment and the latest state root (Query).
      4. snarkVM, compiled to WASM, executes and proves in the browser. It outputs two new records: 100 for Bob and 150 change for Alice. Each is encrypted to its owner and has a commitment.
      5. It builds a fee transition, proves it, and sends the transaction to a snarkOS node.
      6. Validators run check_transaction: they verify the proof, check that the serial number is new, and check the fee. The transaction enters a batch, gets certified, and is committed through a subdag.
      7. This function has no finalize, so speculate just marks it accepted. The block is added: the serial number joins the spent set, and the two commitments join the state tree.
      8. Bob's wallet scans the new block, finds a record that decrypts with his view key, and shows +100.

      The public/private boundary is the design decision

      If the same token used transfer_public, sender, recipient and amount would all be plaintext in the Future and in the mappings, just like on Ethereum. Aleo programs choose per value. Most real programs mix the two: a private transfer, and public supply or compliance state.

      24Who calls snarkVM, and which parts

      snarkOS (validators and clients)Holds a Ledger. Calls check_transaction on mempool entries, prepare_advance_to_next_quorum_block / speculate when building a block, and check_next_block + advance_to_next_block when syncing. Uses the narwhal/* and committee types for consensus messages.
      SDK and walletsUse snarkVM via wasm/: account key generation, record decryption, authorize, execute with a network Query, fee estimation, transaction serialization.
      Leo CLICompiles Leo to Aleo instructions, then uses snarkVM to parse and type-check, evaluate / PackageRun for leo run, and deploy / execute to build real transactions.
      Provers, explorers, indexersProvers run ledger/puzzle. Explorers and indexers deserialize blocks and transactions with snarkVM's own types, so their JSON and byte formats match the chain.

      As an application developer you usually don't import snarkVM directly. You write Leo and use the SDK, and both embed it. You work in snarkVM when you build infrastructure or change the protocol.

      25Working safely in this codebase

      snarkVM is consensus code with deployed versions in the wild. The rules in AGENTS.md follow directly from what you've read:

      • No forks. Same inputs must give the same outputs forever. New behaviour is gated by ConsensusVersion.
      • Console and circuit stay in sync. Change one, check the other, and compare constraint counts.
      • Serialization is consensus. Byte formats feed into IDs and hashes. Round-trips must be exact and backwards compatible.
      • Fail closed. Reject on uncertainty; no panics in production paths. Every unwrap needs a comment saying why it can't panic.
      • Performance matters. Proving and verification dominate costs. Pre-allocate, avoid clones, use rayon where it helps.

      Reading the code yourself

      26A reading plan, and five exercises

      Reading order

      1. synthesizer/program/src/resources/credits.aleo: read a real program, especially transfer_private, transfer_public, fee_private and bond_public.
      2. console/types/field next to circuit/types/field: see the twin pattern on the simplest type.
      3. console/account/src: private key → compute key → view key → address, in about 100 lines.
      4. console/program/src/data/record: encrypt.rs, serial_number.rs, tag.rs, to_commitment.rs.
      5. synthesizer/process/src/stack/execute.rs: execute_function, reading the comments in order.
      6. synthesizer/process/src/trace/mod.rs: prepare, prove_execution, verify_execution_proof.
      7. synthesizer/src/vm/verify.rs and finalize.rs: the validator side.
      8. ledger/src/check_next_block.rs and advance.rs: how a block becomes state.
      9. console/network/src/consensus_heights.rs: how the protocol evolves.
      10. Last and optional: algorithms/src/snark/varuna.

      Exercises

      1. Trace a call. Starting from VM::execute, write down every function called until Trace::prove_execution returns. Note which ones are console-only and which build circuits.
      2. Find the double-spend check. Locate where serial numbers are checked for uniqueness, both within a transaction and against the ledger.
      3. Count constraints. Find a test that compares constraint counts for a circuit type, for example in circuit/types/integers, and run it. Predict whether u64 multiplication or field multiplication costs more, then check.
      4. Follow a rejection. In vm/finalize.rs, find how a failed finalize turns a transaction into RejectedExecute and a Transaction::Fee.
      5. Read a gate. Pick any ConsensusVersion::V14 check in the codebase with grep -rn "ConsensusVersion::V14", and explain what would break on old blocks without it.

      A–ZGlossary

      Authorization
      The set of signed Requests for a call tree. Enough for a prover to execute and prove, but not to change the inputs.
      CallStack
      The mode a function runs in: Authorize, Synthesize, CheckDeployment, Evaluate, Execute or PackageRun.
      Certificate
      A proof that a deployed verifying key was honestly derived from the function's circuit.
      Commitment
      A hiding and binding fingerprint of a record. It's the leaf in the global state tree.
      ConsensusVersion
      A numbered protocol upgrade (V1–V21) that activates at a block height, per network.
      Finalize
      Public, on-chain logic that validators run after ordering. It reads and writes mappings.
      Future
      The output of an async call. It carries the arguments finalize will run with.
      Global state root
      The Merkle root over the ledger that input-record inclusion is proven against.
      Mapping
      A public key→value store belonging to a program.
      Process / Stack
      The registry of programs, and the per-program state (types, keys, checksums) used to run them.
      Record
      An encrypted, owner-bound UTXO: owner, data, nonce, version.
      Serial number
      Published when a record is spent. It's unique per record but unlinkable to its commitment.
      SRS
      Structured reference string: the universal setup shared by all circuits.
      Subdag
      The set of Narwhal certificates committed together. It becomes one block's authority.
      Tag
      Hash(sk_tag, commitment), derived from the graph key. Also recorded on spend.
      tpk / tvk / tcm / scm
      Transition public key, transition view key (a secret), transition commitment, signer commitment.
      Trace
      Collects transitions and circuit assignments during execution, then proves them in one batch.
      Transition
      One function call on chain: program, function name, inputs, outputs and keys.
      Varuna
      snarkVM's Marlin-family zkSNARK with a universal setup and batch proving.
      View key
      Decrypts an account's records. Read-only; can't spend.
