Prover Compute Phases

An hour of GPU time turns one Llama answer into a proof. This page shows where that hour goes: what the machine is doing in each phase, which part of the machine does it, and how long each part took on SASH's published runs.

The one-line version. Most of the hour is the ordinary computer (the host CPU) writing a giant table of numbers and doing the bookkeeping for table lookups. The famous part, hashing and polynomials and FRI, is under five percent of the time, and it runs on the graphics card.

0 · Watch one segment get proved

A request is cut into 290 segments: one layer of the model over 512 token positions. Each segment is proved on its own, in the same nine steps. Press play. The clock runs at the real measured speeds: one segment takes 23.4 seconds when proved on its own.

What the picture shows. Left: the saved numbers come off the disk. Middle: the tape, a big table where every number the rules will check gets its own cell; the smaller table under it holds the lookup fractions. Right: the five Merkle trees that seal the tables, and the dice that are rolled once the tape is sealed. The bar at the bottom is the clock. The three short steps (seal, dice, seal again) are drawn from the STARK and remainder phases, because only the twelve phase totals in section 3 are measured one by one.

1 · The whole run, from prompt to verdict

This is the order the job script runs things on the GPU machine. Amber steps are the prover's own work. Teal steps can be rerun or checked by anyone with the public data. Times are from the main run at a 4,096-token prompt, unless a row says otherwise.

  1. 1

    Make the answer

    Python · on the card

    Take a 4,096-token prompt and let the model write 512 new tokens, always picking the single most likely next token. This is the answer that will be proved. Because the pick is always the top one, the answer is fixed by the numbers and nothing else.

    Kind of work: a normal forward pass, but in the fixed arithmetic: 8-bit integer matrix multiplies, 16-bit floats for the rest, an integer softmax. Every operation is written out separately, which is why it is slow.

    time 197 s logoutput 512 token ids
  2. 2

    Save every number

    Python · on the card, written to disk

    Run the model again over all 4,608 positions and save, for each layer and each block of 512 positions, every number a rule will later check: the 8-bit activations, the exact 32-bit sums, the scales, the attention scores, the keys and values, the running total between layers. This saved set is called the witness.

    Kind of work: five forward passes (layer 0 alone, then eight layers at a time) and a lot of disk writing. About 122 GB in all.

    time 771 s measured in passes of 49, 161, 179, 176 and 206 sabout 0.17 s per position derived
  3. 3

    Plan the segments

    Python · CPU

    Read the saved files, work out the widest numbers any segment will need (so every segment uses the same table sizes), stop early if any layer would overflow the 31-bit field, and write one line per segment: 9 blocks × 32 layers + 2 output-head segments = 290 lines.

    Kind of work: integer bookkeeping. Seconds.

    time not timed in the published numbersoutput plan.txt
  4. 4

    Build the GPU rule checkers

    Rust + CUDA compiler · once per set of shapes

    Every rule in the proof is a small formula. This step turns each distinct formula into GPU code, checks that code against the CPU version on random inputs, and rebuilds the prover with it. The proof comes out byte-for-byte the same either way; this step only decides whether the card or the CPU checks the formulas.

    Kind of work: code generation and compiling. Paid once per machine and reused across contexts.

    time 695 s log (47 kernels, none new, still rebuilt)at the long context 1,204 s measured
  5. 5

    Seal the model

    the weight holder · Rust · once per model

    Build two Merkle trees that do not depend on any prompt and read off their roots. The shape root covers the lookup tables and constants; anyone can rebuild it. The model root covers the 8-bit weights and their scales; only the weight holder can make it, and everyone can compare against it.

    Kind of work: hashing. 22.9 million weight cells and 4.5 million shape cells per position.

    time not timed as a published constantoutput two roots
  6. 6

    Prove all 290 segments

    Rust · card and host · the loop

    Five processes of 64 segments each. While one segment is being proved, the next one is already being loaded and written, so the card is never left waiting for the disk. What happens inside one segment is the animation above and sections 2 to 5.

    Kind of work: the subject of this page.

    loop 3,683 s (61 min) measuredper segment 12.7 s derivedcard memory peak 73.7 GB of 81.6
  7. 7

    Check everything

    Rust · CPU only, no card needed

    For each segment: replay the hashing, rebuild the shape tree and compare roots, compare the model root, run the STARK checker, test the sixteen hand-offs inside the layer. Then check the 537 links between segments, and that each new token is the top pick the previous position's proof says it is.

    Kind of work: hashing, a few hundred Merkle paths, and one big tree rebuild. Section 6.

    total 119 s measuredper segment 0.41 s measured

The timed steps, to scale

Saving, proving and checking are from the main run. The answer and kernel times are from a second run on the same kind of card, so the 5,465 s total mixes two runs. SASH's own "from a cold start" figure, saving plus proving, is 4,454 s, 74 minutes derived. A gate script then throws the run away if any segment skipped a check, any hand-off was left unchecked, any kernel fell back to the CPU, or any link failed.

2 · One segment, step by step

This is the animation in words. The tree numbers are the order they enter the hash. The rule is simple: a tree's root goes into the hash before any random number that depends on it is drawn, so the prover can never fit its numbers to the dice.

  1. a

    Load

    Read this segment's saved numbers off the disk, unpack them, check them against the plan, and lay them out the way the gadgets want them. The first segment of the run read 1.36 GiB.

    phases read, decode, check, construct, alloc, build_restshare of the loop 11.8 %host CPU
  2. b

    Write the tape

    Every gadget writes its numbers into the big table, as numbers mod 231−1. A 16-bit float becomes two cells. A range check becomes a few small pieces. Each lookup becomes a key. The attention scores become the biggest block of all. 58.5 million cells per position.

    phase traceshare 35.4 %mostly host CPU today
  3. c

    Seal trees 0, 1 and 2

    Tree 0 is the shape (the checker can rebuild it). Tree 1 is the model (the weight holder's root). Tree 2 is the tape itself. Sealing means: read each column as a polynomial, evaluate it on twice as many points, hash everything into a Merkle tree.

    inside stwo and prove_restcard
  4. d

    Roll the dice

    Hash the roots so far and read random numbers out of the hash: the point every lookup fraction is taken at, the random vector for the weight-multiply check, the mixing weights. They live in a field of about 2124 values, so guessing is hopeless.

    microseconds
  5. e

    Lookup bookkeeping and GKR

    A lookup says "this value is in that table". The proof handles it with fractions: one fraction per use and one per table row, built from the random number, which must add up to the same total on both sides. A value outside the table can never balance. For the five biggest groups the running totals are not even sealed: a GKR sumcheck shrinks each group to one claim. 17.8 million cells per position.

    phase interactionshare 41.8 %, the biggesthost CPU, in the big extension field
  6. f

    Seal tree 3 and the hand-off trees

    Tree 3 holds the fractions. Trees 4 and up hold what the next segment reads: the running total out of this layer, and the keys and values out of this token block. Their roots are the links the final check compares. 2.6 million cells per position.

    card
  7. g

    The STARK proper

    Check every rule on every row of the extended table (3,872 kernel calls over 32 segments, 0.138 s on the card). Divide out the points where the rules apply; if any rule failed anywhere, this division leaves a remainder. Open everything at one random point. Then fold with FRI until a constant is left, and answer 100 spot checks.

    phase stwoshare 4.6 %about 1.07 s per segment
  8. h

    Write the receipt

    Three JSON files: the statement, the claims, and the proof. The middle-sized proof is 25 MiB in memory and 65 MiB as JSON; the extra is the text encoding, not more proof.

    phase serializeshare 0.5 %

3 · The twelve phases of the loop

SASH timed the loop with one segment at a time over 32 layer segments of the last token block, the one that sees the whole prompt. They did it twice: once with the GPU rule checkers in place, which is the published setup, and once with every checker switched off so the CPU does it. The twelve phases add up to the loop exactly, and the run refuses to publish if they do not.

All twelve rows measured; per-segment values are the row divided by 32 derived. One segment on its own: 23.4 s with the checkers, 148.0 s without. In the main run the loop overlaps one segment's loading and writing with the previous one's proving, and gets down to 12.7 s per segment; the one-at-a-time numbers are the ones that split cleanly.

What the GPU checkers buy. Same 32 segments, same 32 proofs byte for byte: 748 s with the checkers, 4,737 s without, 6.3 times longer. The whole difference is one phase. The STARK goes from 34 s to 3,984 s, from 4.6 % of its loop to 84 %. The same 3,872 rule evaluations cost 0.138 s on the card and 3,950 s on the host. The other eleven phases barely move.

5 · Inside the STARK second

Per segment, the proof system itself takes about one second on the card. SASH splits it in two: the commit path (turn columns into polynomials, stretch them, hash them into trees) and the prove call (check the rules, divide, open at a random point, fold with FRI).

commit path170.8 s over 290 segments, 0.59 s each measured prove call114.4 s, 0.39 s each derived stwo total285.2 s, 0.98 s each measured split60 % commit, 40 % prove derived

So the card seals a segment's 1.25 billion fresh cells, plus the two sealed-once trees, in about six tenths of a second. The host CPU manages 15.9 million cells per second on the same job (microbenchmark), which is why this part lives on the card.

The right-hand timers include host-side work, so they overlap the prove_rest phase and add to more than the 34 s STARK phase. They show the order and the proportions, not a second clean split.

What each piece does, in one line each

  • Interpolation. Read each column as the values of one polynomial. The column's length is the degree limit.
  • Stretching (low-degree extension). Evaluate that polynomial on twice as many points. This is why every rule must be degree 2 or less: the quotient has to fit in the stretched table.
  • Merkle hashing. Blake2s over the stretched column, one tree per stage. The root goes into the transcript, and the dice come out of it.
  • Rule checking. Apply every rule to every row of the stretched table. Card: 3,872 kernel calls, 0.138 s. CPU: 3,950 s. This is the only thing the generated kernels do.
  • Quotient. Divide the combined rule polynomial by the polynomial that is zero on the rule rows. A broken rule leaves a remainder, and the quotient stops being low degree.
  • Out-of-domain opening. Open every polynomial at one random point outside the table to tie the quotient to the columns.
  • FRI. Fold the opened polynomial in half, seal, fold again, until a constant is left; the checker asks for 100 random paths. Without this, a prover could pass the random point with numbers that lie on no polynomial at all.

6 · Checking the proof

The checker never touches the card. For each segment it does, in order:

  1. 1

    Replay the hashing

    Hash the roots in the proof in the same order the prover did and re-derive every dice roll. A prover who rolled before sealing cannot reproduce this.

  2. 2

    Rebuild the shape tree, compare roots

    From the public parameters, build tree 0 again and check its root against the statement. On a small machine this is the slow step.

  3. 3

    Compare the model root

    The root in the statement must equal the one the weight holder published. The checker never sees a weight.

  4. 4

    Run the STARK checker

    Check the 100 FRI paths, the Merkle openings, the random-point consistency, and replay the five GKR sumchecks against their link claims.

  5. 5

    Check the sixteen hand-offs

    Inside the layer: the seven places the running total is passed on, the three float-to-8-bit seams, attention, the weight-multiply check, the two block boundaries, the embedding on layer 0, the strict top-pick on the head.

  6. 6

    The grid

    Between segments: 281 links down the layers (the running total's root) and 256 links along the prompt (the keys and values' roots). Then the token chain against the prompt and the top picks.

Why the host is the limit, and what moving it buys

The phase split says it plainly. Writing the tape (35 %) and the fraction bookkeeping (42 %) are host CPU work, and with loading they are about 89 % of the loop. The card sits idle for most of a segment's life. Issue 12 moves that work onto the card one gadget at a time.

Both big phases are partly on the card already, which is why the tape factor is only 1.4. The projection's split (fractions 49 %, tape 30 %, STARK 9 %, read 5 %) was taken from an older H200 run; the split measured here on the published setup is 42, 35, 4.6 and 0.5. SASH keeps the projection on its original assumptions and says so.
